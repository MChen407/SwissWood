# Rapport de mise en place de la base de données et du déploiement Prisma sur Railway

## 1. Contexte

Le projet **SwissWood** est une application composée d'une API développée avec **Node.js, Express et TypeScript**. La gestion des données est assurée par **MySQL**, avec **Prisma** comme outil de gestion de la base de données.

L'API a été déployée sur **Railway**. Cependant, la base de données MySQL associée au projet était initialement vide et aucune installation complète de la base de données n'avait été réalisée en local.

L'objectif était donc de mettre en place la base de données directement sur Railway, tout en permettant à l'application de gérer automatiquement les changements futurs de structure.

---

## 2. Préparation du modèle de données

Le modèle de données du projet a été défini dans le fichier :

`prisma/schema.prisma`

Ce fichier décrit les principales données utilisées par l'application, notamment :

* les utilisateurs ;
* les produits ;
* les avis clients ;
* les favoris ;
* les commandes ;
* les articles des commandes ;
* les paiements ;
* les messages de contact ;
* les contenus administrables.

Le modèle utilise MySQL et des identifiants uniques pour les différentes données.

Une vérification du fichier a également été réalisée afin de s'assurer que le modèle était correctement reconnu par Prisma.

---

## 3. Création de la première migration

Une première migration appelée **`0_init`** a été créée à partir du modèle de données.

Cette migration contient les instructions nécessaires pour créer les tables de l'application dans MySQL.

Le fichier est conservé dans le projet :

`prisma/migrations/0_init/migration.sql`

Cette étape est importante car elle permet de conserver une trace des changements effectués sur la base de données et de reproduire la même structure sur les différents environnements.

---

## 4. Correction d'un problème avec MySQL

Lors du premier déploiement de la migration sur Railway, une erreur est apparue concernant les valeurs par défaut utilisées sur certains champs de type texte et JSON.

MySQL n'acceptait pas certains champs `TEXT` ou `JSON` avec une valeur par défaut définie directement dans la création des tables.

La migration a donc été corrigée afin d'être compatible avec MySQL.

Une nouvelle vérification du modèle et du fichier de migration a ensuite été effectuée.

---

## 5. Gestion de la première migration échouée

La première tentative d'installation de la base de données n'a pas été complète. Certaines tables avaient été créées avant que la migration ne rencontre une erreur.

Prisma considérait alors la migration comme ayant échoué, ce qui empêchait les nouvelles tentatives.

La situation a été analysée à partir de l'état réel de la base de données et de l'historique des migrations.

Les anciennes traces de cette tentative ont été nettoyées afin de repartir sur une base cohérente.

---

## 6. Installation de la base de données sur Railway

Une fois la migration corrigée et la base remise dans un état propre, la migration initiale a été exécutée directement depuis l'environnement Railway.

La commande utilisée a permis d'appliquer la migration :

`0_init`

Le résultat final a confirmé que la migration avait été correctement appliquée :

**"All migrations have been successfully applied."**

La base de données contient maintenant les principales tables nécessaires au fonctionnement de SwissWood :

* `users`
* `refresh_tokens`
* `products`
* `product_reviews`
* `favorites`
* `orders`
* `order_items`
* `payments`
* `cms_content`
* `contact_messages`

Une table supplémentaire, `_prisma_migrations`, est utilisée par Prisma pour conserver l'historique des migrations.

---

## 7. Mise en place du remplissage initial

Une fois la structure de la base créée, le fichier de données initiales (`prisma/seed.ts`) a été exécuté.

Cette étape permet d'ajouter automatiquement les premières données nécessaires au fonctionnement et aux tests de l'application.

Le remplissage initial a été exécuté avec succès à l'aide de la commande :

`npx prisma db seed`

La base contient donc désormais non seulement sa structure, mais également les données prévues par le fichier d'initialisation.

---

## 8. Configuration du démarrage de l'application

Le démarrage de l'API est configuré de manière à vérifier les migrations avant de lancer le serveur.

La commande utilisée est :

`prisma migrate deploy && node dist/server.js`

Cela signifie que lors du démarrage de l'application :

1. les éventuelles nouvelles modifications de la base sont vérifiées ;
2. les nouvelles migrations disponibles sont appliquées ;
3. l'API est ensuite démarrée.

Cette organisation permet d'éviter de devoir modifier manuellement la base de données à chaque nouvelle version du projet.

---

## 9. Fonctionnement pour les prochaines modifications

La base de données est maintenant prête pour les évolutions futures.

Lorsqu'une modification sera apportée au modèle de données, une nouvelle migration devra être créée.

Par exemple, si un nouveau champ est ajouté à un utilisateur, une nouvelle migration sera créée plutôt que de modifier directement la migration initiale.

Les migrations seront ensuite envoyées avec le code du projet.

Lors du prochain déploiement sur Railway, la nouvelle migration sera automatiquement appliquée.

La migration initiale `0_init` ne doit donc plus être modifiée.

---

## 10. État actuel du projet

À la fin de cette intervention :

* la base MySQL Railway est opérationnelle ;
* le modèle Prisma est validé ;
* la migration initiale est correctement installée ;
* les tables principales ont été créées ;
* les données initiales ont été ajoutées ;
* le système de mise à jour de la base est configuré ;
* l'API peut démarrer avec la base de données Railway ;
* les futures modifications pourront être gérées avec de nouvelles migrations.

## Conclusion

La base de données de **SwissWood** est maintenant correctement intégrée à l'environnement Railway.

Le projet dispose désormais d'une structure de données stable et d'un système permettant de suivre les évolutions de la base de données au fur et à mesure du développement.

Cette mise en place permet également de séparer clairement le code de l'application et la gestion de la base de données, tout en garantissant que les modifications futures pourront être reproduites automatiquement lors des déploiements.
